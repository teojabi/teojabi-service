# 기획/설계 문서 교차 검토 리포트 (Review Report)

현재까지 작성된 `RESEARCH.md`, `spec.md`, `infra.md`, `schema-design.md`, `api-design.md`, `frontend-design.md` 문서들을 기반으로 상호 일관성 및 실제 구현 시 누락되거나 충돌할 수 있는 사항들을 면밀히 검토하고, **구현 단계 진입 전 사전에 준비해야 할 사항**들을 도출한 최종 리포트입니다.

## 1. 아키텍처 충돌 해결 완료 (Resolved)
*   **해결된 이슈**: 초기 설계 시 존재했던 **Next.js SSR(NextAuth.js) 환경과 정적 FTP 배포(Porkbun) 간의 치명적 충돌** 이슈는 프레임워크를 걷어내고 **순수 HTML/JS/CSS(Vanilla JS)** 기반으로 전환하면서 완벽히 해소되었습니다.
*   **현 상태의 강점**: 빌드 파이프라인이 극도로 단순화되었으며(`npm build` 불필요), 네이버 지도와 같은 외부 바닐라 스크립트와의 호환성이 매우 높아졌습니다.

## 2. 추가 고려사항 및 스펙 보완 필요 항목 (Important)

### 2.1 인증(JWT) 관리의 보안성 확보 방안 부족
*   **이슈**: `frontend-design.md`와 `api-design.md`에 프론트엔드가 토큰을 쿠키(Cookie)나 로컬 스토리지에 보관한다고 명시되어 있습니다.
*   **보완점**: XSS(교차 사이트 스크립팅) 공격에 대비하여, 백엔드(NestJS)에서 소셜 로그인 롤백 응답 시 토큰을 클라이언트 JS가 직접 다루지 못하도록 **`HttpOnly`, `Secure`, `SameSite` 속성이 적용된 쿠키**로 구워주는 방식을 최우선으로 고려해야 합니다. (이 경우 프론트엔드의 `auth.js`는 토큰 유무 검증만 제한적으로 수행하는 방향으로 설계 수정 권장)

### 2.2 공공데이터 프록시 API의 속도/부하 문제 (Rate Limiting & Caching)
*   **이슈**: `api-design.md`의 `Proxy` API들은 백엔드를 거쳐 국토부 실거래가 및 토지이음 API를 실시간 호출합니다. 
*   **보완점**: 공공데이터 포털은 일반적으로 초당 요약 호출 횟수(TPS) 제한과 일일 할당량이 존재합니다. 사용자가 지도를 드래그할 때마다 불필요한 Proxy 호출이 폭주할 수 있으므로, NestJS 백엔드 단에 **Redis를 활용한 캐싱(Caching) 레이어 도입** 또는 브라우저 단에서의 **디바운싱(Debouncing) 로직**(`js/pages/search.js`) 설계가 명확히 문서에 추가되어야 합니다.

### 2.3 CORS (교차 출처 리소스 공유) 설정
*   **이슈**: Porkbun(정적 호스팅)과 NCP(API 허브) 도메인이 분리됨에 따른 통신 거부 이슈.
*   **해결안**: NestJS의 `main.ts`에 프론트엔드 도메인만 허용하는 화이트리스트 방식의 CORS 설정과 인증 쿠키 전달을 위한 `credentials: true` 설정을 문서 스펙(`spec.md`)에 공식 요구사항으로 반영했습니다.

### 2.4 지도 화면(`search.html`) 좌/우 레이어 및 갤러리 연동(`properties.html`) 투트랙 최적화
*   **이슈**: 기존에 하나의 상세페이지로만 통일하려 했으나, 갤러리에서 진입할 때 지도를 거쳐 오른쪽 패널로 보는 것이 UX 상 어색할 수 있습니다.
*   **해결안**: 하이브리드 투트랙 방식을 스펙에 명시했습니다.
    *   **지도 검색 (`search.html`)**: 지도 위에서 일반 주소 클릭 시 **왼쪽 공공데이터 팝업**, 마커 클릭 시 **오른쪽 다이내믹 팝업**을 사용.
    *   **갤러리 검색 (`gallery.html`)**: 갤러리 게시판에서 특정 썸네일을 클릭하면 완전한 단독 상세 페이지 화면인 `properties.html`로 진입하여 데이터를 풀 사이즈로 조망.

## 3. 구현 단계 진입 전 사전 준비(Pre-requisites) 사항

코드를 작성하기 전, 멘토/관리자급에서 사전에 인프라 상에서 세팅하고 식별자(Key/Secret)를 확보해 두어야 하는 목록입니다. 이 항목들이 준비되지 않으면 개발이 부분적으로 블로킹될 수 있습니다.

1. **최초 공공데이터 일괄 적재 (Bulk Load)**
   - 캐시 미스(Cache Miss)를 예방하기 위해, **서비스 런칭 전 최초 1번**, 필요한 지역 범위의 일반 부동산 공공정보를 `PublicData` 테이블로 대량 주입(Script/Query)하는 작업이 수행되어야 합니다.

2. **소셜 로그인 앱 등록 (OAuth 2.0 Credentials)**
   - 네이버, 카카오, 구글 플랫폼에 애플리케이션 생성 및 콜백 URL 등록.

3. **최초 관리자(ADMIN) 권한 커스텀 부여**
   - 소셜 로그인으로는 `USER` 등급만 확보되므로, 서비스 런칭 전 백엔드 관리자가 Supabase Dashboard(SQL Editor)에 진입하여 자신의 튜플 `role` 필드를 `ADMIN`으로 수동 UPDATE하는 1회성 절차가 필요합니다.

4. **오브젝트 스토리지 (Supabase Storage) 세팅**
   - 관리자가 매물(Property)에 이미지를 올릴 때 파일이 물리적으로 저장될 **Supabase Storage Bucket**과 퍼블릭 CDN 권한 설정이 사전에 완료되어야 합니다.

5. **외부 API 접근 Key 발급 및 GitHub Secrets 등록**
   - 네이버 지도 SDK (Client ID)
   - 국토부 실거래가/공시지가 및 토지이음 API Key
   - FTP 시크릿, NCP SSH, Supabase DB Connection URI 등을 Action Secrets로 등록.

## 총평
프론트엔드를 순수 정적 파일로 전환한 결정은 시스템 구조를 단순화하고 초기 설계 충돌을 명확하게 해결한 아주 훌륭한 선택이었습니다. 

위 2항(보안/캐시 설계 보완)과 3항(API Key 및 외부 서비스 초기 세팅)만 코드 착수 전에 조율된다면, 인프라 구축 단절 없이 매끄러운 개발 레이어 전개가 가능할 것입니다.
