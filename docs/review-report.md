# 기획/설계 문서 교차 검토 리포트 (Review Report)

현재까지 작성된 `RESEARCH.md`, `spec.md`, `infra.md`, `schema-design.md`, `api-design.md`, `frontend-design.md` 문서들을 기반으로 상호 일관성 및 실제 구현 시 누락되거나 충돌할 수 있는 사항들을 면밀히 검토하고, **구현 단계 진입 전 사전에 준비해야 할 사항**들을 도출한 최종 리포트입니다.

## 1. 아키텍처 충돌 해결 완료 (Resolved)
*   **해결된 이슈**: 초기 설계 시 존재했던 **Next.js SSR(NextAuth.js) 환경과 정적 FTP 배포(Porkbun) 간의 치명적 충돌** 이슈는 프레임워크를 걷어내고 **순수 HTML/JS/CSS(Vanilla JS)** 기반으로 전환하면서 완벽히 해소되었습니다.
*   **현 상태의 강점**: 빌드 파이프라인이 극도로 단순화되었으며(`npm build` 불필요), 네이버 지도와 같은 외부 바닐라 스크립트와의 호환성이 매우 높아졌습니다.

## 2. 기존 스펙(Spec) 보완 반영 사항 (Important)

### 2.1 인증(JWT) 관리의 보안성 확보 방안 (반영됨)
*   **이슈**: 초기 프론트엔드가 토큰을 쿠키나 로컬 스토리지에 보관한다고 명시되어 발생할 수 있는 보안 취약점.
*   **보완점**: 백엔드(NestJS)에서 소셜 로그인 응답 시 클라이언트 JS가 직접 다루지 못하도록 **`HttpOnly`, `Secure`, `SameSite` 속성이 적용된 쿠키**로 직접 구워주는 방식이 `api-design.md` 스펙에 공식 반영되었습니다. 프론트엔드는 토큰 유무 검증만 제한적으로 수행합니다.

### 2.2 공공데이터 프록시 API의 속도/부하 문제 (반영됨)
*   **이슈**: 실시간 Proxy 호출 시 발생하는 공공데이터 포털의 지연 및 일일 할당량(Rate Limiting) 제한.
*   **보완점**: 백엔드에 **주기율 스케줄러(CRON) 기반의 캐싱 레이어 도입**이 스펙으로 정리되었으며, 데이터를 `PublicData` 테이블에 주기적으로 적재해 부하를 분산시키기로 협의되었습니다.

### 2.3 CORS (교차 출처 리소스 공유) 설정 (반영됨)
*   **이슈**: 정적 호스팅(Porkbun)과 백엔드 서버(NCP) 도메인 분리에 따른 통신 문제.
*   **보완점**: 백엔드 `main.ts`에 프론트엔드 도메인만 허용하는 CORS 화이트리스트 및 `credentials: true` 속성을 활용한 통신 구조가 스펙으로 포함되었습니다.

### 2.4 지도(`search.html`) ↔ 갤러리(`gallery.html`) 연동 하이브리드 UI (반영됨)
*   **이슈**: 하나의 화면에 여러 정보를 담기 위한 UX(사용자 경험) 고민.
*   **보완점**: 지도 검색에서는 좌/우 슬라이딩 팝업(Layered Popup)으로 공공데이터 및 예약 패널을 띄우고, 갤러리 검색에서는 전용 단독 뷰(`properties.html`)로 넘어가는 투트랙 방식이 `frontend-design.md`에 명시되었습니다.

## 3. [신규 집중 분석] 갤러리 게시판 파일 업로드(DB + Storage) 사전 준비 사항

요청하신 `Supabase` 데이터베이스(Database)와 스토리지(Storage)를 함께 사용하여, 매물 갤러리에 이미지 파일을 업로드하고 연동하기 위한 세부 구현 및 점검 사항을 도출했습니다.

### 3.1 인프라 및 Supabase 구조 검토
1. **Public 버킷 생성 및 정책**:
   * 이미지 업로드를 받을 전용 버킷(예: `post-images`)을 생성해야 합니다. 갤러리에서 누구나 사진을 보아야 하므로 필수로 **`Public` 버킷 설정**이 되어야 합니다.
2. **보안 제한(Restrictions) 설정**:
   * 대시보드 권한 부분에서 허용 확장자(`image/jpeg`, `image/png`, `image/webp` 등)와 5MB 이하 등의 **최대 파일 크기 제한**을 물리적으로 설정하여 악성 업로드를 막아야 합니다.
3. **RLS (Row Level Security)**:
   * 읽기(SELECT)는 누구나 가능하지만 업로드(INSERT)는 `ADMIN` 권한을 가진 인증된 유저만 할 수 있도록 정책(Policy) 쿼리를 준비해야 합니다.

### 3.2 백엔드 (NestJS) 설계 요구사항
1. **파일 파싱 모듈 연동 (Multer)**:
   * 프론트에서 온 `multipart/form-data` 파싱을 위해 `@nestjs/platform-express` 패키지의 `FileInterceptor`를 컨트롤러 메서드에 적용합니다.
2. **이중 유효성 검사 (ParseFilePipe)**:
   * 버퍼로 수신받은 파일을 스토리에 보내기 전에, 백엔드 단독으로 `FileTypeValidator`, `MaxFileSizeValidator`를 이용해 다시 검수합니다. (프론트 단독 검증은 우회가 쉬움)
3. **업로드 트랜잭션 (Atomic Flow & Rollback)**:
   * **과정**: (1) 메모리상의 파일을 Supabase Storage SDK를 통해 지정된 버킷으로 전송 ➡️ (2) 업로드 성공시 반환된 경로로 `getPublicUrl()`을 호출하여 영구 주소 획득 ➡️ (3) 주소와 텍스트 데이터(`title`, `description`)를 `Property` 테이블에 Prisma를 통해 `INSERT`.
   * **롤백(Rollback)**: 파일은 저장되었으나 DB 삽입이 모종의 이유(데이터 누락 등)로 실패한다면 불필요한 고아 파일이 생기므로, 실패 즉시 방금 올린 파일을 버킷에서 스스로 삭제해 버리는 오류 처리 로직이 에러 바운더리에 포함되어야 합니다.
   * **충돌 방지 파일명**: 스토리지에 같은 이름의 파일이 업로드되어 덮어써지는 것을 막기 위해 `Date.now() + UUID` 등의 난수화된 파일명을 자동 생성해야 합니다.

### 3.3 프론트엔드 (Vanilla JS/HTML) 설계 요구사항
1. **FormData 자바스크립트 객체 활용**:
   * 매물 등록 폼(`<form>`) 제출 시 기본 기능을 막고(`e.preventDefault()`), `new FormData()` 객체에 스토리지로 보낼 파일(File)과 데이터베이스에 저장될 텍스트 정보들을 묶어 백엔드로 POST 전송(Fetch)합니다.
2. **클라이언트 1차 UI 검증 유효성**:
   * `<input type="file" accept="image/*" multiple>` 태그를 사용합니다.
   * `change` 이벤트 리스너를 달아서 사용자가 이미지를 첨부하자마자 JS 단에서 파일 크기(예: `file.size > 5 * 1024 * 1024`)를 계산해 경고창(Alert)을 선제적으로 띄워 서버 부하를 막습니다.
3. **UX (업로드 로딩 피드백 및 미리보기)**:
   * 이미지 파일 업로드는 시간이 걸릴 수 있습니다. 사용자가 "저장" 버튼을 여러 번 누르는 것을 막기 위해, 클릭 시 버튼을 **`disabled` 처리하고 로딩 스피너(Loading Spinner)**를 노출시켜 진행 상황을 안내해야 합니다.
   * (권장) `FileReader` API 나 `URL.createObjectURL`을 이용해 저장 전 브라우저에서 이미지를 미리 보여주는 썸네일 박스를 띄우는 것이 UI 적으로 우수합니다.

## 4. 총평 및 사전 이행 준비(Pre-requisites) 사항

현 시점의 아키텍처 및 설계 문서는 프론트엔드 정적 파일 분리와 Supabase 연동, 소셜 로그인 롤백 등 모든 모순점이 명쾌하게 해소된 훌륭한 상태입니다. 

이제 실제 코드 구현에 돌입하기 앞서, 다음과 같은 **초기 환경 인프라 세팅(Key 발급 및 세팅)** 사항을 인지하고 준비해 주세요.

1. **소셜 로그인 앱 등록 (OAuth 2.0 Credentials)**
   * 네이버, 카카오, 구글 플랫폼에 애플리케이션 생성 및 콜백 URL 등록.
2. **Supabase 환경 세팅 사항**
   * 프로젝트 생성 후 URL 및 Service Role 키를 백엔드 `.env`에 설정.
   * `post-images` (Public) Storage 버킷 생성.
   * (런칭 고려) ADMIN 권한 수동 부여 세팅 방법 확보.
3. **최초 공공데이터 일괄 적재 (Bulk Load)**
   * 빈 화면 방지를 위해 런칭 전 지정된 범위의 실거래가 등을 `PublicData`에 최초 일괄 SQL 입력할 배치 스크립트를 따로 구상합니다.
4. **외부 API 접근 Key 발급 및 세팅**
   * 네이버 지도 SDK `Client ID` 및 검색 API 시크릿 발급.
   * GitHub Actions Workflow에 사용될 FTP, SSH 호스트 시크릿 등록.

위 사항들이 검토되고 준비되었다면, 언제든지 **Supabase 데이터베이스 연동 및 갤러리 업로드 코드 구현** 단계로 넘어갈 수 있습니다.
